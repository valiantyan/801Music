# SPEC-ROOM-003 增量同步与删除对账（Phase 3）

## 1. 背景与问题

全量扫描成本高，库非空时重复全量扫描会造成性能与电量浪费。结合低端设备风险评估，本阶段采用“手动触发增量扫描”策略，避免每次启动触发后台同步带来的 CPU 与电量压力。

## 2. 目标（Goals）

- 提供手动触发的增量扫描能力。
- 新增或变更文件可及时入库。
- 删除文件可被识别并移除。

## 3. 非目标（Non-Goals）

- 不在启动阶段自动执行增量扫描。
- 不引入后台调度框架（如 WorkManager）自动周期同步。
- 不实现跨设备同步。

## 4. 范围（Scope）

### 4.1 In Scope

- 手动触发 `MANUAL_INCREMENTAL` 扫描模式。
- 基于 `lastSyncToken` 查询增量变更并 upsert。
- 增量完成后执行删除对账。
- 维护 `library_sync_state` 的 token 与状态字段。

### 4.2 Out of Scope

- 启动自动增量同步。
- 周期性后台任务。
- 云端同步。

## 5. 工作流（Workflow）

### 5.1 入口条件

- 用户在列表页点击“扫描新音频”并选择“增量扫描”。
- 已有可用 `library_sync_state`。

### 5.2 主流程

1. 读取 `lastSyncToken`。
2. 查询 `MediaStore.DATE_MODIFIED > lastSyncToken` 的数据。
3. 对变更项执行 upsert。
4. 执行删除对账，移除库中不存在项。
5. 更新 `lastSyncToken`、`lastScanAt`、`lastScanStatus`。
6. 返回列表并刷新数据。

### 5.3 异常流程

- 查询失败：状态置为 `FAILED`，保留旧库与旧 token。
- 对账失败：记录错误并保留已有数据，不清空全库。
- 用户取消：停止同步，不更新 token。

### 5.4 退出条件

- 至少满足其一：
1. 增量数据已写库并刷新列表。
2. 错误可见且旧数据完整保留。

## 6. 需求定义

### 6.1 功能需求（FR）

- FR1：增量同步使用 `DATE_MODIFIED > lastSyncToken` 查询变更。
- FR2：变更数据 upsert 入库并更新 `lastSyncToken`。
- FR3：同步后进行删除对账，移除库中不存在的记录。
- FR4：增量同步仅由用户手动触发。
- FR5：启动阶段默认不触发增量同步。

### 6.2 非功能需求（NFR）

- 增量扫描不阻塞首屏展示。
- 同步失败不影响现有库可读性。
- 在低端设备上避免启动时 CPU 突增。

## 7. 设计方案

### 7.1 同步服务

- 新增 `AudioLibrarySyncService`（纯业务类）。
- 提供 `incrementalSync()` 与 `fullScanAndRebuild()`。

### 7.2 Token 维护

- `lastSyncToken` 记录本次同步中最大的 `DATE_MODIFIED`。
- 同步失败或取消时不更新 token。

### 7.3 删除对账策略

- 同步结束后获取 MediaStore 当前 ID 集。
- 与本地库 ID 集对比，删除不存在项。
- 默认采用硬删除。

## 8. 交互与 UX

- 增量扫描从手动入口触发，不在启动时自动执行。
- 扫描进度复用现有扫描页显示。

## 9. 验收标准（DoD）

- AC1：用户手动触发增量扫描后，新增文件可见。
- AC2：删除文件在对账后被移除。
- AC3：增量同步失败不影响现有库。
- AC4：库非空启动时不自动触发增量任务。

## 10. 测试计划

- 单元测试：
- 仅更新变更项，未变更项不重复写入。
- 删除对账后本地数据与 MediaStore 一致。
- 失败与取消场景不更新 token。

- 集成测试（Robolectric）：
- 手动触发增量扫描后数据刷新正确。
- 冷启动场景不自动执行增量扫描。

## 11. 监控与可观测性

- 记录增量扫描开始、完成、失败日志。
- 记录 `lastSyncToken` 变更前后值。

## 12. 发布与回滚

- 通过功能开关上线手动增量模式。
- 失败时可回退到手动全量扫描模式。

## 13. 风险与应对

- 风险：MediaStore 查询差异导致漏同步。
- 应对：保留手动全量扫描入口作为兜底。
- 风险：删除对账误删。
- 应对：先灰度放量并记录删除计数告警。

## 14. 兼容性与权限

- 依赖现有存储权限与 MediaStore 访问权限。
- API 24+ 维持一致行为。

## 15. 安全与隐私

- 不上传用户媒体元数据。
- 仅处理本地文件元信息。

## 16. 依赖与前置

- 依赖 Phase 1 的 Room 表结构与同步状态。
- 依赖 Phase 2 的手动扫描入口。

## 17. 决策结论

- 增量扫描采用手动触发，不在启动阶段自动执行。
